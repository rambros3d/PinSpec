# Design

## Context

See proposal.md for motivation and the delta spec for behavior. Current state:

- `src/core/types.ts` defines `ChipData` and `CatalogIndexEntry` with no module field. `PackageInfo.hasExposedPad` already covers physical exposed pads; it is unrelated to module identity.
- `tools/data-gen/adapters/esp32/modules.ts` derives module records from acquired KiCad symbol names using the WROOM/MINI pattern and resolves `baseFamily` from acquired first-party family names. `tools/data-gen/adapters/esp32/index.ts` passes the `EspModule` record into `buildEspChip()` in `join.ts`, which currently uses only its flash evidence.
- `PerimeterPackage.svelte` draws one body group, a subtle inner die outline, centre markings, and perimeter pads inside a single `geometryTransform` group. Centre markings already use `centreLabelAngle` so their text is upright at every rotation. `GridPackage.svelte` renders grid parts; module parts are perimeter QFN-like shards.
- Quick search, the MCU switcher, and the compatible-MCU finder read `CatalogIndexEntry` objects from the catalog store. `PresetGrid.svelte` holds a curated starter-chip array and receives no catalog data; `LandingPage.svelte` is its only host.
- Generated data is gitignored. STM32 golden hash tests hash only STM32 adapter output, so an additive ESP32 field cannot change them.

## Goals / Non-Goals

**Goals:**

- Publish module identity as generated data with the same provenance rules as other ESP32 facts.
- Make module packages visually distinct on the canvas without duplicating pad geometry or interaction logic.
- Make module identity visible in all catalog discovery surfaces, including starter chips.
- Keep version-2 persistence, pin interactions, other vendors, and STM32 generated bytes unchanged.

**Non-Goals:**

- No curated module list, transcribed datasheet value, or static module overlay.
- No separate module renderer component or new package geometry model.
- No change to grid packages, exposed-pad geometry, bonded-pin handling, mux labels, exporters, or solver behavior.
- No workspace state field, share payload field, project-file field, or new localStorage preference.
- No new dependency, backend, source acquisition, or change to `dataUrl()` path handling.

## Decisions

1. **Additive metadata in core types, not in workspace state.** Define a `ChipModuleMetadata` interface in `src/core/types.ts` with `kind: 'module'`, `name`, `baseFamily`, and `symbol`, and add `ChipData.module?: ChipModuleMetadata` plus `CatalogIndexEntry.module?: boolean`. The full record stays in the shard; the index carries only a compact marker because discovery needs a tag, not the symbol provenance. A bare die omits the field entirely rather than declaring `kind: 'die'`, which keeps absence unambiguous and avoids a second enum. Alternative considered: storing a module flag in `WorkspaceState`; rejected because module identity is catalog data, not shareable pin configuration or a UI preference.

2. **Generate from the existing module join.** Keep `buildEspModules()` as the single evidence source. In `buildEspChip()`, emit the module record only when an `EspModule` input is present, taking `name` from its id, `baseFamily` from the resolved first-party family, and `symbol` from the acquired KiCad symbol. `indexEntry()` sets the marker only when the shard record is present, using a conditional spread so JSON contains no `undefined` key. MPN-only parts and bare dies receive no module input and therefore no field. Alternative considered: detecting modules in the UI from part-name regular expressions; rejected because it creates second, handwritten chip data outside the generator.

3. **Gate in the ESP32 adapter, alongside its existing strict gates.** Add one gate that checks the WROOM reference part has module metadata, that `ESP32-C3` and `ESP32-C3FH4` do not, and that every index marker agrees with its shard. It reuses `GateContext` and returns the existing `esp32` vendor result shape. A failure blocks artifact writes through the same orchestrator path as the current ESP32 pad and matrix gates. Alternative considered: a global gate over all vendors; rejected because module evidence is vendor-specific and the global gates already cover index and budget integrity.

4. **Decorate the existing perimeter body group.** Add a derived `isModule` flag in `PerimeterPackage.svelte` and a module-only branch inside the current body `<g>` in the rotated geometry group. The branch draws a PCB-style outer outline, a dashed inner die rectangle, castellated half-hole marks aligned to the existing placed pads, and the module name text. All new marks are `pointer-events="none"`, sit behind or alongside the existing text, and use existing theme utility classes such as `fill-base-100`, `stroke-base-300`, and `fill-base-content`; no raw color literal and no new token. The existing centre markings, pin numbers, pad rectangles, tags, and bonded treatment stay as they are. Alternative considered: a separate `ModulePackage.svelte`; rejected because it would duplicate layout, rotation, tag, hit-area, and tooltip logic.

5. **Upright text through the existing centre-label angle.** The module name uses the same `centreLabelAngle` transform as the other centre markings. Because decorations live inside `geometryTransform`, they rotate with the body at 90, 180, and 270 degrees while the name remains readable. No change to `localLabelAngle`, `isQuarterTurn`, SVG extent swapping, or `PackageCanvas` fit view is needed. Alternative considered: counter-rotating the whole module group separately; rejected because it would desynchronize castellations from pads.

6. **One shared MODULE tag helper pattern in discovery.** Quick search, the MCU switcher, and the compatible-MCU finder render a compact badge when `entry.module === true`. `LandingPage.svelte` derives a set of module part ids from `catalogStore.index` and passes it to `PresetGrid.svelte`; the grid renders the tag only for ids in that set. Before the catalog loads, no tag is shown. Alternative considered: adding a `module: true` literal to the curated `STARTER_CHIPS` entry; rejected because that would be a handwritten chip fact and could disagree with generated data.

7. **Test updates are scoped to the changed contracts.** `tests/data-gen-esp32.test.ts` asserts module metadata on module shards, its absence on dies and MPNs, and gate failures. `tests/core-io.test.ts` and `tests/exporters-vendor.test.ts` keep their schema coverage and add metadata acceptance without changing version-2 payload expectations. `tests/ui-multi-vendor.test.ts` asserts the tag strings and their absence for dies. `tests/theme-tokens.test.ts` keeps the no-raw-color and no-emoji scans. `tests/package-rotation.test.ts` asserts that module decorations are inside the rotated group and the name uses the upright centre-label angle.

## Risks / Trade-offs

- [Castellations could overlap pads or capture clicks] Mitigation: draw them inside the body edge with `pointer-events="none"` and keep pad rectangles, `data-pin-pos`, and handlers untouched.
- [Module tag could disagree with catalog data] Mitigation: derive every tag from the generated index marker and assert shard/index agreement in the generation gate.
- [Decorative marks could use colors that fail the theme audit] Mitigation: reuse existing theme utility classes and keep the raw-color scan in place.
- [Extra shard and index fields could affect artifact size] Mitigation: the record is small, appears only on module parts, and remains subject to the 150 MB budget gate.
- [Golden output changes could be misattributed to STM32] Mitigation: the STM32 adapter and its golden hashes are untouched; generation tests continue to hash STM32 output separately.
- [Source-string assertions could overfit renderer internals] Mitigation: assert the presence of the module branch, rotation group membership, and theme-only styling rather than exact SVG path coordinates.

## Migration Plan

1. Add the two type fields, then emit module metadata in the ESP32 join and index entry, with the new strict gate.
2. Add the module-only decoration branch to `PerimeterPackage.svelte` and verify rotation and interaction contracts.
3. Add the MODULE tag in the three catalog result surfaces and derive starter-chip tags from the catalog index.
4. Update the six affected test files and run the full verification sequence: `npm test`, `npm run check`, `BASE_PATH="/pinspec/" npm run build`, and `npm run gen-data`.
5. After all tasks pass, the implementation agent runs `openspec archive module-package-visual -y` and includes the synced spec and archived change files in the implementation commit. This planning step makes no commit.

## Open Questions

None. Module evidence, visual scope, tag surfaces, and persistence boundaries are fixed by the request and the delta spec.
